# Support and feedback

No staffed service, retention policy, or response-time promise is provided.
The owner decides those separately before making public commitments.

Start with the help command and `docs/chat-acceptance.md`. The reference keeps
data only in memory: a new process starts empty. It cannot recover a previous
session, sync devices, execute arbitrary instructions, or publish a release.
Explain those limitations before asking someone to rely on it.

For a defect, request a synthetic minimal reproduction, command grammar used,
expected/observed behavior, candidate binding, environment class, and consent
to retain the report. Do not request credentials, complete chat histories,
private paths, customer names, or real checklist contents by default.

Use `templates/feedback.json` for local intake. Mark whether a report was
actually observed, reproduced, or only hypothesized. Empty feedback is not
proof of satisfaction. Distinguish usability, reliability, correctness, privacy,
and optional refinement; retain inconvenient reports.

Pass bounded references to the CEO's review and product's iteration plan.
Close only against evidence on a named candidate. When public sharing is
appropriate, prepare a separate synthetic reproduction and sanitized summary
for owner approval; never copy the local report store.
